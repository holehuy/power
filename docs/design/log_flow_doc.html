IPAM Worker Logging Flow

How the 5 Workers and 2 shared infrastructure modules (SharePointClient, NotificationClient) write logs — from a Write-InfoLog call down to Windows Event Log and the file log. This is a reference document, not a step-by-step guide.

Scope src/common/Common.psm1 · src/config/log-*.json 16 standardized codes 7 registered Worker-IDs 4 log levels
About This Document

This document describes the logging architecture and flow of the IPAM Worker system (functions, Code convention, Worker-ID registry, message catalog, LogLevel) — for reference when developing or maintaining Workers, investigating incidents via Event Log/file log, or building a Code tracking sheet in Excel. Content is cross-checked directly against the current source code; this is not an operations runbook.

01 — Overview

One call, one of two entry paths, one write destination

All 4 public functions (Write-InfoLog / -WarningLog / -ErrorLog / -DebugLog) pass through one shared internal engine before reaching Windows Event Log or the file log. No Worker is permitted to call Write-WorkerLog directly.

Write-InfoLogLevel = Information
Write-WarningLogLevel = Warning
Write-ErrorLogLevel = Error, always written
Write-DebugLogLevel = Debug, not written to Event Log
4 functions → 1 engine
Write-CodedLogInternal Accepts -Code OR -Message (-Code takes priority) · validates prefix matches the calling function · resolves EventId
2 Worker-ID sources
-Code 'ERR-ALLOC-0001' Worker-ID read directly from Code → look up catalog by prefix → substitute {{Token}}
-Message "..." Worker-ID obtained from Get-CurrentWorkerId (set via Set-CurrentWorkerId at script start)
EventId = WorkerIdEventIdBase[Worker-ID]
Write-WorkerLog Filters by LogLevel (Error always passes) · attaches EntryType · writes output
Windows Event Log "IPAM-Worker" 512MB, overwrite mode · does NOT accept Debug
File log logs/worker-yyyy-MM-dd.log · accepts all 4 levels
The 2 shared infrastructure modules (SharePointClient.psm1, NotificationClient.psm1) do not run on a Task Scheduler cycle — they always use -Code (never -Message), so their logs never depend on the Get-CurrentWorkerId of whichever Worker happens to call into them.

03 — Naming Convention

Code = <PREFIX>-<Worker-ID>-<XXXX>

Three hyphen-separated parts. Level is not stored in the JSON — it IS the PREFIX, and PREFIX must match the calling function.

PartValid ValuesRole
PREFIXINFO · WARN · ERR · DEBUGLevel — must match the calling function (Write-ErrorLog only accepts Codes starting with ERR-); a mismatch throws immediately.
Worker-IDALLOC · SYNC · DEL · ARP · MON · SHAREPOINT · NOTIFDetermines the default EventId (see table 04) — must be pre-registered in $script:WorkerIdEventIdBase.
XXXX0001 – 9999A freely chosen sequence number — only needs to be unique within the same Worker-ID + PREFIX combination. Not required to be contiguous.

06 — LogLevel

4 Levels, Filtered Before Write

Configured via the IPAM_WORKER_LOG_LEVEL environment variable or Set-WorkerLogLevel — defaults to Information.

LevelOrderFiltered when threshold is higher?Written to Event Log?Written to file log?
Debug 0 Yes No — Event Log has no Debug level Yes
Information 1 Yes Yes Yes
Warning 2 Yes Yes Yes
Error 3 No — always written regardless of threshold Yes Yes

Error unconditionally bypasses the filter to preserve the "no silent errors" principle (§8.4) — even if someone misconfigures the threshold.

07 — Design Decisions

Why This Approach, Not the Alternatives

Flat per-Worker EventId, not per Level/Seq
Write-EventLog -EventId only accepts 0–65535. Keeping IDs both unique and spanning the full 0001–9999 Seq range for every Worker × Level × Seq combination would require roughly 150,000 values — far beyond the limit. Simplified to 1 EventId per Worker; precise identification lives in the Code string inside the Message body, not in the EventId.
-Code takes priority over -Message when both are passed
Avoids ambiguity when a call accidentally passes both — behavior must be deterministic, independent of parameter order.
SharePointClient / NotificationClient always use -Code, never the ambient Worker-ID
These 2 modules can be called from any Worker. If their own logging depended on Get-CurrentWorkerId, a single missing Set-CurrentWorkerId call somewhere could cause the error-reporting path itself to throw — unacceptable for error-handling code.
Function names use Write-*Log, not Write-Info/-Warning/-Error
Write-Warning and Write-Error are built-in PowerShell cmdlets — reusing those names would shadow the originals throughout the entire scope where the module is imported.
4 separate catalog JSON files per Level, not one shared file
Level is not stored inside the JSON itself — splitting the files by Level makes the file's location part of the Level declaration, so content and metadata can never drift apart.
MON is not listed in the official Worker table
The original design (simple_design.md) refers to this component as "監視スクリプト" (a Script, not a Worker) — table 4.2 has no row for it, only a separate "※" footnote. The architectural reason: this is the only read-only component, with no write permission (§9.1/§10.4).
_comment_ entries in JSON
JSON has no real comment syntax — these are fake keys (ordinary strings) that exist purely to visually group entries for human readers. They never parse as a valid Code, so Get-LogMessageTemplate never touches them.
